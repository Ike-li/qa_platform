**文件**: `/.github/workflows/ci.yml`

**新增**:
```yaml
jobs:
  doc-health-check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v6
      - name: Check document health

          chmod +x scripts/check-docs.sh
```

**价值**:

### 6. Doc Health Skill 设计

**文件**: `/docs/DOC_HEALTH_SKILL_DESIGN.md`

**设计亮点**:

**产品定位**: 让文档像代码一样可测试、可维护的 Claude Code Skill

**核心功能**:
```bash
/doc-health check           # 运行所有检查
/doc-health check --links   # 只检查断链
/doc-health check --fresh   # 只检查新鲜度
/doc-health fix             # 自动修复
/doc-health init            # 初始化配置
/doc-health report          # 生成报告
```

**技术架构**:
- 模块化设计（checks/ + fixes/ + core/）
- 配置驱动（.doc-health.yaml）
- 支持多种报告格式（Markdown、HTML、JSON）
- 自动修复能力

**检查项矩阵**（8 项）:
| 检查项 | 优先级 | 可自动修复 |
|--------|--------|-----------|
| 断链检测 | P0 | ❌ |
| 关键文档存在性 | P0 | ⚠️ 部分 |
| 日期标记验证 | P1 | ✅ |
| 文档新鲜度 | P1 | ❌ |
| 代码引用验证 | P1 | ⚠️ 部分 |
| 版本号一致性 | P2 | ❌ |
| CLAUDE.md 漂移 | P2 | ❌ |
| 术语一致性 | P2 | ❌ |

**实施计划**:
- Phase 1: MVP (1 周) - 核心检查功能
- Phase 2: 增强 (1 周) - 高级功能
- Phase 3: 打磨 (3 天) - 开源准备

## 💭 经验总结

### 做得好的地方

1. **调研先行** - 花时间研究业界实践，避免重复造轮子
2. **循序渐进** - 先修复现有问题，再设计新工具
3. **文档驱动** - 先写设计文档，确保方向正确
4. **CI 集成** - 自动化执行，不依赖人工记忆

### 可以改进的

1. **测试覆盖** - 修复脚本后应该添加自动化测试
2. **渐进式推出** - 可以先在本项目试用一段时间再产品化
3. **性能考虑** - 大型项目文档检查可能较慢，需要优化

### 关键教训

**"不要一次性检查所有历史文档"**

这是所有调研工具都强调的原则：
- ❌ 错误：第一次运行就检查所有文件 → 500 个问题 → 没人修 → 检查变成噪音
- ✅ 正确：只检查变更文件 → 逐步清理历史债务 → 可持续维护
