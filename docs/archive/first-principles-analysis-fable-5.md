## 0. 方法声明：对"需求"做第一性原理，意味着什么

第一性原理不是"把架构简化到最小"，而是把问题拆到**不可再拆的事实**，然后只从这些事实向上重新推导——过程中禁用三样东西：

1. **类比**（"成熟平台都有 RBAC，所以我们也要"）
2. **惯性**（"PRD 里写了，所以它是需求"）
3. **沉没成本**（"已经写了 2 万行，所以架构应该保持"）

对"需求"而言，最根本的拆解是：**需求 = 一个真实的人 + 一个真实场景 + 愿意支付的转换成本**。三者缺一，那不叫需求，叫功能清单。本文从这个定义出发。

## 1. 公理层：三组不可争辩的事实

### 1.1 关于这个项目的存在状态

| 事实 | 数据 | 来源 |
|------|------|------|
| 项目年龄 | 26 天（2026-05-15 启动） | git log |
| 提交数 | 449（单日峰值 80） | git log |
| 产品代码 | 后端 21K 行 + 前端 11.8K 行 | wc -l |
| 测试代码 | 66.7K 行（产品代码的 **3.2 倍**） | wc -l |
| 文档 | 45 篇、11.5K 行 | wc -l |
| 工程健康度 | 4.7/5.0，"可以上线" | DASHBOARD.md |
| **真实用户数** | **0** | product.md §7 全部基线为 0；§9 下个里程碑第一条是"收集 1-2 个真实 QA 项目的接入证据" |
| 当前工作流向 | BACKLOG 全部已完成项与待办项均为内向型工程任务（覆盖率、CI、文档健康、依赖），**无一项指向获取用户** | docs/BACKLOG.md |

这组事实合在一起构成本次分析的起点：**一个工程上接近完美、但从未接触过任何真实用户的系统。** 任何对它的"需求重审"如果不从这一点开始，都是在回避主要矛盾。

### 1.2 关于"测试执行"这个领域的物理本质

- 测试的本质产出不是"运行结果"，而是**发布决策所需的信心**。所有人付钱（或付时间）买的是后者。
- 执行 = 代码 × 环境 × 算力 × 调度。这四个要素在 2026 年已全部商品化：Git、Docker/OCI、云、CI。GitHub Actions 对私有仓库每月有免费额度，自建 GitLab Runner / Jenkins 在国内团队是存量标配。**"一个能跑测试的地方"不稀缺。**
- 稀缺的是**解读**：这次失败是新 bug、flaky 还是环境问题？这个 git ref 能不能发？哪些测试在长期说谎、在浪费算力？
- 解读依赖的核心资产是**用例级、跨时间的结构化历史**——而这恰好是 CI 系统天然不保存的（CI 以"构建"为中心，日志即弃、结果不结构化）。这是真实存在的缺口。

### 1.3 关于用户行为的物理本质

- 用户迁移工具当且仅当 **新增价值 > 转换成本**。转换成本 = 迁移 + 学习 + 信任建立 + 双轨维护。
- "把测试执行搬到一个新平台"是转换成本谱系的**最高端**：要重配环境、凭证、调度，还要与现有 CI 共存。
- "在现有 CI 末尾加一行上传结果"是转换成本谱系的**最低端**。
- 市场已经用脚投票验证了这一点：Datadog Test Optimization、Trunk Flaky Tests、BuildPulse、Currents、Allure TestOps——这一代测试智能产品**全部寄生于现有 CI，只收结果、不抢执行**。

## 2. 从公理重推需求栈

### 2.1 根需求只有三个问题

剥到最底层，目标用户（QA 工程师 / 测试经理）的根需求是三个问题，没有第四个：

1. **"能不能发？"** —— 发布信心（release confidence）
2. **"为什么红？"** —— 失败归因（新 bug / flaky / 环境）
3. **"哪些测试在说谎或浪费？"** —— 测试资产健康（flaky、慢、死测试）

注意根需求清单里**没有**"我需要另一个跑测试的地方"。执行只是满足根需求的一种手段，而且是已被商品化的那种手段。

### 2.2 从根需求推导的最小价值链

```
结构化结果 (JUnit XML)            ← 输入，唯一硬依赖
   → 跨时间历史对比                ← 变化检测：新增失败 / 恢复
      → 归因（flaky 排除）          ← 回答"为什么红"
         → release summary + 通知   ← 回答"能不能发"
```

**关键发现：这条价值链，平台已经全部建成了。** JUnit 解析、Analytics 趋势、flaky 检测、`release-summary`（raw / flaky-adjusted 通过率、新增失败、恢复用例）、条件通知——product.md §9 的 Beta 能力描述实际上已经把价值重心移到了这里。

### 2.3 错位：价值在链的末端，门槛却设在链的起点

当前产品要求用户**先迁移执行**（建项目 → 配凭证 → 配 Pipeline → 配环境 → 在平台容器里跑），才能获得链末端的分析价值。也就是说：

> **平台把转换成本最高、稀缺度最低的环节（执行），设置成了获得转换成本最低、稀缺度最高的价值（解读）的前提条件。**

这是当前需求设计中最深的一处结构性错位。它不是工程缺陷——执行引擎本身做得很好（OOM 识别、取消、worker_lost 回收、凭据注入）——它是**价值排序**的错位。顺带一提：执行引擎同时也是整个系统中维护成本最高的部分（Docker socket 提权面、OOM 检测竞态、worker 心跳回收……修复记录都在 git 历史里），却是差异化最弱的部分。

## 3. 三个被沉默跳过的第一性问题

### 第 0 问：用户需要一个新的"执行场所"吗？

PRD 检验过 8 个设计假设（多租户、SSE、S3……），但没有检验第 0 个假设：**"测试需要在我们的平台上执行"**。

- 对**已有 CI** 的团队（绝大多数有自动化测试的团队）：不需要。他们需要的是 CI 之上的解读层。
- 对**没有 CI** 的团队：需要执行，但这个群体通常也还没有值得分析的自动化测试资产，不是 ICP（理想客户画像）。
- 真正可辩护的执行场景是窄的：定时巡检（不绑 commit 的回归）、需要特殊隔离/资源的测试、不方便进 CI 的手工触发。这些是"增值选项"，不是"准入门槛"。

**推论：执行引擎应该从"必经之路"降级为"可选能力"。** 工程上的对应动作小得不成比例：增加一个 `POST /api/v1/runs/import`（接收 JUnit XML + git_ref + 元数据，复用现有 collector、租户、Analytics、通知的全部管线），用户在任何 CI 里加一条 curl 即可接入。现有约 80% 的资产原样复用，转换成本从"迁移执行"塌缩为"加一行"。

### 第 1 问：这个项目的真实需求，是谁的需求？

证据（个人仓库、26 天 449 commits 的 AI 辅助节奏、3.2:1 的测试代码比、45 篇文档、全部内向型任务偏好、零用户）指向：到目前为止，这个项目实际满足的需求大概率不是 PRD 里那个"日均触发 20-50 次执行的 QA 工程师"（该画像是合成的，从未被任何真实个体确认过），而是以下一种或几种：

- **A. 能力证明 / 作品集**：用 AI 辅助在 4 周内独立建成一个企业级质量的全栈平台——这本身就是作品，且已接近最优状态。
- **B. AI 辅助工程方法论的试验场**：CLAUDE.md 协议、文档健康体系、冒烟测试框架、多模型 review 流程——这些**过程资产**的密度远超一个内部工具的需要，它们本身可能就是真正的产出。
- **C. 真实产品**：服务真实 QA 团队。这个需求**到今天仍是假设**，没有任何证据支持或反对它。

这三种定位不互斥，但它们推出**完全不同的最优下一步**：

| 定位 | 最优下一步 | 当前行为是否服务于它 |
|------|-----------|---------------------|
| A 作品集 | 收口；写 showcase（demo GIF、架构决策记录、复盘文章）；开始下一个项目 | ❌ 再提 7 个点覆盖率对作品集边际价值≈0 |
| B 方法论 | 把 CLAUDE.md 协议、文档体系、冒烟框架提炼成可迁移模板/文章 | ❌ 这些资产散落在仓库里，未提炼 |
| C 产品 | import API + 找到第 1 个真实试点 | ❌ BACKLOG 无一项指向它 |

**当前的行为模式（持续投入工程打磨）不在任何一种定位的最优路径上。** 这是比"架构是否过度设计"更根本的需求问题。

### 第 2 问：为什么所有能量流向打磨，而不是验证？

不是疏忽——product.md §9 白纸黑字写了下一步是找试点。是因为两类任务的性质不同：

- 提升覆盖率/修 CI/理文档：**可解的、确定的、有即时反馈的**，且恰好是 AI 辅助开发最擅长加速的任务类型。
- 找第一个真实用户：**不可控的、反馈缓慢的、可能收到否定答案的**。

工具的便利塑造了努力的方向。当"做工程"的成本被 AI 压到极低，工程任务就会无限填满日程——这正是过去一周发生的事（覆盖率 0%→83.1% 用了一天，而"收集 1-2 个真实接入证据"在文档里躺了 6 天没有动作）。**在零用户状态下，每一分投入工程打磨的努力，边际价值都趋近于零；而第一个真实用户的边际价值是无穷大——因为它决定 C 定位是否成立，从而决定后续所有投入的意义。**

## 4. 与 Opus 4.8 分析的分歧

那份分析有价值（成本侧的拆解是扎实的），但它做的是**实现的第一性原理**，不是**需求的第一性原理**。具体分歧：

1. **它问"这个系统能不能造得更便宜"（300-500 行 MVP），没问"这个系统该不该以执行为中心"。** 便宜地造一个不稀缺的东西，仍然不稀缺。它检验了 8 个假设，漏掉了第 0 个。
2. **它把"已投入大量工作（覆盖率 90%+）"列为保持当前架构的理由。** 这是沉没成本谬误——第一性原理首先要求排除的就是它。架构该不该保持，只取决于它是否服务于被验证的需求，与已投入多少无关。
3. **它的建议停在"上线后收集使用数据"。** 但零用户时，"上线后看数据"是一个永远不会被触发的条件分支。先有用户，才有数据。
4. **它的结论"是企业级平台、不是个人项目"把定位当成了事实。** 定位 C 目前是未验证假设；把假设当事实，会让后续所有推理看起来严谨实则悬空。

## 5. 行动推导

### 5.1 无论哪种定位都成立的动作（本周）

1. **冻结过剩打磨**：覆盖率、文档健康、依赖更新类任务全部移出高优先级。4.7/5.0 的工程质量对 0 个用户是过剩库存。
2. **建 import 路径**（估 1-2 天）：`POST /api/v1/runs/import` 接收 JUnit XML + git_ref，复用现有 collector → Analytics → 通知管线。这是现有资产的最高杠杆复用，同时服务定位 A（展示产品 sense）和定位 C（砍掉接入门槛）。
3. **Dogfooding——平台的第一个用户应该是它自己**（估 半天）：本仓库自己就有 2137 个后端测试 + 151 个前端测试在 CI 里每天跑。让 CI 把 JUnit 结果 import 进一个部署实例，平台立刻拥有第一个真实租户、真实数据流、真实的 flaky/趋势/release-summary 画面。
4. **连续 7 天自己当用户**：每天用平台（而不是 GitHub Actions 页面）回答"今天的 main 能不能发"。诚实记录：哪天你没打开它？为什么？——**如果连作者本人都不用它做发版判断，合成画像里的 QA 工程师更不会。** 这是成本最低的需求证伪实验。

### 5.2 按定位分流的动作（下周起，按 7 天实验结果决策）

- **实验结果"我每天都在用"** → C 定位获得第一份证据：找 1 个外部真实项目试点（朋友的团队 / 开源项目的 CI），目标指标就用 product.md §9 已定义的 `time-to-first-green-run` 和 `7 日内二次触发率`。
- **实验结果"我自己都不看"** → C 定位被自己证伪，止损：把项目按 A 收口（写复盘 showcase：架构图 + 26 天 449 commits 的过程叙事 + 关键技术决策），把 B 的过程资产（CLAUDE.md 协议族、文档健康体系、冒烟框架）提炼成独立模板仓库或文章。**这不是失败，A+B 的产出本身已经超过大多数 side project。**

### 5.3 可证伪性声明

本分析的核心论断及其证伪条件——出现以下证据即应推翻对应结论：

| 论断 | 证伪条件 |
|------|---------|
| "执行不稀缺，解读才稀缺" | 找到 ≥3 个愿意把执行迁移过来（而不是只上传结果）的真实团队 |
| "C 定位是未验证假设" | 任何 1 个非作者本人的真实用户连续 7 天使用 |
| "继续打磨的边际价值≈0" | 某个具体工程缺陷被证明阻挡了真实用户接入 |
| "dogfooding 是有效的最小实验" | 作者的开发流程与目标用户差异大到结果不可迁移（例如平台目标场景是必须隔离执行的硬件测试） |

## 6. 一句话总结

> 这个项目用 26 天证明了"能不能建成"（答案：能，且质量过剩），但还没有开始回答"该不该存在"（对谁、以什么形态）。下一周最有价值的工作不在代码里——在第一个真实用户（哪怕是项目自己）的使用记录里。执行引擎是你最贵的资产，也是用户最不需要先付钱的部分：把 import 做成前门，把执行降为选配，然后用 7 天 dogfooding 给 C 定位一个可证伪的判决。

**适用场景**: 定位决策、投入方向纠偏、与 opus-4.8 版本的平行对照
