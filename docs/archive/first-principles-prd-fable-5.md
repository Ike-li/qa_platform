# TestSignal（测试信号台）— 第一性原理 PRD

**作者**: Claude Fable 5（max effort）
**日期**: 2026-06-10
**写法声明**: 本文档从根问题与公理出发独立推导，不参考 qa_platform 现有 PRD 与代码结构；与现有资产的映射仅作为附录 B。外部数据均标注来源。

---

## 0. 一句话定义

> **TestSignal 是测试结果的记忆与判断层：它让你已经在跑的测试变得可信。**

电梯陈述：你的 CI 每天产出几十次红绿灯，但红绿灯是健忘的——它不记得这个用例上周也红过、不知道这次红是不是老毛病、说不出"这个版本能不能发"。TestSignal 提供两个入口：（1）接收任何 CI 上传的测试结果（一行配置接入），或（2）代跑没有 CI 的定时回归测试。为每个测试用例建立跨时间的履历，把"红了"翻译成"新增失败 2 个、已知 flaky 3 个、可以发"。

---

## 1. 根问题：红绿灯的三个物理缺陷

软件团队每天在两个时刻做决策：**merge 时刻**（这个 PR 能合吗）和 **release 时刻**（这个版本能发吗）。决策的输入是测试结果，而测试结果今天的呈现形式——CI 红绿灯——存在三个不可回避的结构性缺陷：

### 缺陷 1：信号是概率的，呈现是二值的

对 Travis CI 的大规模研究发现，**47% 的失败构建在重启后直接通过**——将近一半的红灯是噪声而非事故。Atlassian 测得 Jira Frontend 仓库 **21% 的 master 构建失败由 flaky 引起**。但红绿灯只有红和绿，它把 47% 的噪声和 53% 的真实事故渲染成同一种颜色。

### 缺陷 2：判断需要历史，CI 不保存历史

回答"这个失败正常吗"需要知道这个用例过去 30 天的表现。CI 系统以"构建"为中心：日志即弃、结果非结构化、用例级历史不存在。每次看到红灯，工程师都在零历史条件下重新人肉判断——而这个判断本可以被数据回答。

### 缺陷 3：损害是行为性的，且自我强化

这是最贵的缺陷。一旦工程师学会"有些红是噪声"，行为就开始退化：先重跑再思考、红着也敢合、code review 时无视失败。**信任一旦流失，测试套件的全部投资同时贬值**——几万行测试代码还在运行、在消耗算力，但已经没有人相信它说的话。58% 的开发者每月至少遭遇 flaky，其中 79% 认为是中度以上问题；受 flaky 困扰的团队占比三年内从 10% 涨到 26%（Bitrise，2022→2025）。

**根需求由此得出：把测试结果从"一次性的二值红绿灯"，变成"可累积、可解读、可信任的决策信号"。**

---

## 2. 为什么是现在（2026）

两个趋势让这个问题在当下急剧恶化，构成产品的时代窗口：

1. **AI 生成测试的信号污染**。AI 已贡献约 16.4% 的新增测试提交（AIDev 数据集），业界普遍观察到"覆盖率显著上升、生产事故率持平甚至上升"——大量 AI 生成的测试是变更探测器而非回归捕捉器，近重复用例泛滥、对实现细节过耦合。测试的**数量**在爆炸，**信号密度**在稀释。生成测试的工具已经满地都是；**治理测试信号的层无人做**。
2. **解读层在海外已被验证、在国内是空白**。Datadog Test Optimization、Trunk Flaky Tests、BuildPulse、Currents、CloudBees Smart Tests 验证了"寄生于 CI、只收结果、卖解读"的形态（详见附录 A）；而国内开源生态（MeterSphere 13k stars 等）全部聚焦"测试资产的创建与管理"（用例管理、接口测试），**测试结果智能层没有占位者**，且国内对自托管、钉钉/企微/飞书集成、对接自建 GitLab/Jenkins 有刚性偏好，海外 SaaS 难以覆盖。

## 3. 公理

以下五条是本 PRD 的全部依据。**每个功能必须能追溯到至少一条公理；追溯不到的，无论多常见，不做。**

| # | 公理 | 内容 |
|---|------|------|
| A1 | 价值公理 | 测试的唯一产出是发布信心。执行是手段，信心是产品。 |
| A2 | 商品化公理 | "跑测试的地方"已被商品化（GitHub Actions / GitLab / Jenkins 免费或存量）；"用例级跨时间历史"无人保存。价值只在后者。 |
| A3 | 转换成本公理 | 接入成本必须显著低于痛感。痛感是"每周被噪声红灯打断几次"量级，所以接入必须是"CI 里加一行"量级。要求用户迁移执行的设计自动出局。 |
| A4 | 信任公理 | 判断系统的信任逐次建立、一次摧毁。错误的自动阻断（把真失败标成 flaky 放行）比不阻断危害大一个数量级。默认给证据、不给命令；自动化动作必须用户显式开启，且永远可一键追溯原始数据。 |
| A5 | 行为公理 | 不改变行为的信号没有价值。每个展示必须回答"所以我现在该做什么"，并附带完成该动作的最短路径。仪表盘本身不是产品，被影响的决策才是。 |

## 4. 产品边界

### 4.1 做什么

**双入口**：
- 入口 A：代跑测试（容器化执行 + cron 定时）- 覆盖无 CI 的定时巡检场景
- 入口 B：接收结构化测试结果（CI 末尾上传 JUnit XML）- 零迁移成本接入

**单核心**：
建立用例级履历 → 区分信号与噪声 → 在 merge/release 时刻输出判断依据 → 驱动 flaky 治理行为。

### 4.2 坚决不做什么（每条标注推导来源）

| 不做 | 推导 |
|------|------|
| **不做 CI**（构建、部署、流水线编排） | A2：执行已商品化 |
| **不管理测试用例**（用例编写、计划、评审） | 那是"测试资产创建层"（MeterSphere / TestRail 的领域）；我们是"测试信号解读层"。两层的数据模型、用户时刻、竞争格局完全不同 |
| **不默认阻断 merge** | A4：自动阻断的 false positive 会一次性摧毁信任。PR comment 提供证据；阻断作为 v2 显式开启项 |
| **不做 AI 生成测试** | 与定位对位：我们是 AI 测试泛滥的治理层，不是泛滥源 |

### 4.3 双入口策略（2026-06-11 决策记录）

产品定位为**测试信号解读层**，但提供两个入口以覆盖不同场景：

**入口 A：平台代跑**（执行引擎）
- **场景**：独立 QA 团队维护外部项目的每日回归测试；项目无自建 CI 或 CI 能力受限
- **形态**：容器化执行 + cron 定时触发
- **定位**：补充能力，非核心差异化
- **取舍**：引入 ~30% 额外代码复杂度，但覆盖"无 CI 的定时巡检"场景（§4.2 原文提及的远期选配场景）

**入口 B：结果导入**（核心入口）
- **场景**：已有 CI 的开发团队，CI 末尾一行上传 JUnit XML
- **形态**：POST /runs/import 接收结构化结果
- **定位**：核心价值入口，零迁移成本（A3）
- **对标**：BuildPulse / Datadog Test Optimization 的"寄生于 CI"模式

**单核心**：测试结果的记忆与解读
- 失败分诊（为什么红）
- 发布判断（能不能发）
- Flaky 治理（哪些测试在说谎）

**权衡说明**：
- 入口 A 偏离 A2（执行已商品化），增加维护成本
- 但覆盖真实存在的"独立 QA 团队代跑"场景
- 产品对外宣传仍强调"测试信号解读层"，入口 A 作为可选能力
- 架构保持：执行路径产出 Run → 进入解读层（与导入路径汇合）

## 5. 用户

### 5.1 ICP（理想客户画像）

同时满足：自动化测试 ≥ 200 个用例；CI 每天 ≥ 10 次运行；近一个月发生过"主干红了但没人能立刻说清为什么"。**不满足 ICP 的团队（测试少、跑得少）痛感不足，不是目标用户，不为其设计。**

### 5.2 关键 persona：红灯守门人

不按职位（QA / 开发 / 经理）定义用户，按**角色时刻**定义：每个团队都存在一个"红灯守门人"——CI 红了之后被打断去判断"真坏了还是又抖了"的那个人（可能是 QA，可能是轮值工程师，可能是 EM）。守门人的一天：

- 被动时刻（每天 N 次）："CI 红了" → 需要 30 秒内分类：新增失败 / 已知 flaky / 持续失败
- 主动时刻（每周 1-2 次）："发版前" → 需要回答"这个 ref 相对上个 release 的质量变化"
- 治理时刻（每月）："受够了" → 需要知道哪几个用例浪费了最多时间，修复或隔离它们

三个时刻分别对应第 6 节的三个核心视图。

### 5.3 中国语境的形态约束

自托管优先（数据不出门）、单机可部署（运维能力有限的团队）、通知一等公民是钉钉/企业微信/飞书（Slack 通过 webhook 覆盖）、Git 提供方包含自建 GitLab 与 Gitee。

## 6. 需求推导

格式：**D-x（公理来源）→ 需求 → 验收标准**。验收标准必须可测试。

### D1. 用例履历（核心对象模型）（A2）

**TestCase（跨 run 的稳定身份）是第一公民，Run 只是观测事件。** 所有价值（趋势、flaky、新增/恢复）建立在"同一用例的跨时间观测序列"上。

- 身份解析规则：`suite + class + name` 归一化；参数化用例（如 pytest 的 `test_x[param]`）默认折叠到母用例、可展开；同一 run 内的 retry 记录为同一观测的多次尝试，不产生重复用例。
- **验收**：同一用例改个参数值不会断履历；重试不会让一个用例在一次 run 里出现两行；用例改名提供手动合并履历的入口（自动改名探测不承诺）。
- 这是本产品最难也最值钱的技术资产：身份解析做错，上层一切分析都是垃圾。

### D2. 一行接入（A3）

唯一接入方式：CI 末尾上传 JUnit XML（业界事实标准，pytest/Jest/Go/JUnit/Playwright 全部支持输出）+ git 元数据（ref、sha、branch）。提供三种等价形态：`curl`、单二进制 CLI、GitHub Action / GitLab CI include。

- **验收**：一个有 JUnit XML 输出的项目，从注册到第一次数据进站 ≤ 10 分钟、CI 配置改动 ≤ 5 行；上传 API 对脏数据宽容（缺字段降级收录，不拒收）。
- 明确不支持：要求改测试代码、装 SDK、改测试框架的接入方式一律不做。

### D3. 冷启动诚实（A3 + A4）

价值按数据量分层兑现，且**永远不假装确定**：

- 第 1 次上传后 5 分钟内：套件结构、用例数、最慢 Top10、失败列表——立刻有東西可看。
- 第 2 次上传起：与上次 run 的 diff（新增失败 / 恢复 / 仍失败）。
- 约 2 周 / 50 次 run 后：flaky 判定达到可用置信度。
- **验收**：所有统计类结论必须展示样本量与置信级别（如"flaky：基于 14 天内 37 次观测，同 SHA 翻转 4 次"）；数据不足时显示"观察中（还需 N 次 run）"，禁止在低样本下输出确定性结论。

### D4. 三个核心视图（根需求 → 三问）

**D4a. 失败分诊（"为什么红？"）—— 被动时刻，使用频率最高**

每次 run 的失败自动分为三类：**新增失败**（该用例近 N 次观测均通过，本次首次失败）/ **已知 flaky**（履历中存在同 SHA 翻转或高翻转率）/ **持续失败**（连续 ≥ K 次失败，已是存量问题）。

- **验收**：红灯守门人打开 run 页 30 秒内能完成分诊（新增失败置顶、全文错误消息与堆栈直接展开、附该用例履历迷你图）；同类失败（相同错误签名）自动聚类折叠。

**D4b. 发布判断（"能不能发？"）—— 主动时刻，价值密度最高**

输入 `ref` + `baseline`（默认上个 tag / main），输出 verdict：原始通过率、**flaky 调整后通过率**、相对 baseline 的新增失败清单、恢复清单、新增用例数。

- **验收**：verdict 一页呈现且可链接分享；每个数字可下钻到用例级证据（A4：给证据不给命令——结论是"flaky 调整后 100%，新增失败 0"，决定权在人）。

**D4c. 资产健康（"哪些测试在说谎/浪费？"）—— 治理时刻，长期价值**

flaky 排行榜：**按造成的损失排序**（阻塞的 run 数 × 平均时长 + 触发的重跑），不按翻转率排序——排序错了治理动作就不会发生（A5）。另含：最慢用例、僵尸用例（持续失败超 30 天无人修——参考 Microsoft "两周不修即移除"策略带来 18% flakiness 下降的证据）。

- **验收**：榜单每项展示"过去 30 天浪费了 X 分钟 CI / 阻塞 Y 次"；提供该用例完整观测履历作证据。

### D5. 行为闭环（A5）

每个信号附带最短动作路径：

- 失败分诊页 → 一键生成 issue（带履历链接与错误聚类）/ 一键标记 quarantine 建议（产出配置片段或 PR，由用户合入，不偷偷改行为——A4）。
- verdict → 一键分享只读链接（给不登录平台的决策者）。
- 通知规则：仅在**状态变化**时打扰（首次新增失败、flaky 转持续失败、通过率跌破阈值），渠道为钉钉/企微/飞书/Webhook。
- **验收**：通知默认配置下，纯 flaky 翻转不产生通知（不然产品自己变成噪声源，自我否定）。

### D6. 机器可消费（A5 + 2026 现实）

数据出口与人口同权重：完整 REST API；PR comment（GitHub/GitLab，非阻断）；**MCP server**——让用户的 AI 编程助手（Claude/Cursor）能直接问"这个 PR 的失败哪些是 flaky""这个用例的履历"。2026 年红灯守门人的很大一部分判断发生在 AI 助手对话里，BuildPulse 已验证此接口形态。

- **验收**：MCP 暴露 ≥3 个工具（查 run 分诊、查用例履历、查 verdict）；PR comment 在 run 完成后 1 分钟内出现。

## 7. 非功能需求（只列影响形态的）

| 维度 | 要求 | 推导 |
|------|------|------|
| 部署 | 单机单进程 + 单 PostgreSQL 可跑全功能；Docker Compose 一条命令 | A3 延伸：运维成本也是转换成本 |
| 容量假设 | 单实例支撑 50 项目 × 日 500 run × 5000 用例（约 250 万观测行/天），Postgres 分区即可，不引入额外存储系统 | 形态简洁是功能（对照附录 A：竞品最大差评是部署/接入重） |
| 数据保留 | 用例级观测默认 180 天（flaky 统计需要长窗口），run 原始 XML 30 天 | D1 服务 |
| 多租户 | v1 单租户多项目；多租户推迟到有 ≥2 个真实组织共用一个实例的证据出现 | A3 + 证伪纪律：不为假想的规模付复杂度 |
| 安全 | 上传走项目级 token；只读分享链接带过期 | 最小充分 |

## 8. 成功指标与证伪条件

### 北极星

**每周"被影响的决策"次数**：有真人基于平台输出做出 merge / release / 修复或隔离 flaky 的动作次数。
**显式反指标：上传量**。CI 自动上传不代表任何人在听——它是虚荣指标，禁止出现在任何汇报里。

### 阶段 gate（每阶段不过 gate 不进下一阶段）

| 阶段 | 时长 | Gate（通过才继续） | 证伪含义 |
|------|------|--------------------|----------|
| v0 dogfooding | 1 周 | 作者本人连续 7 天用它（而不是 CI 页面）判断 main 状态 | 作者都不用 → 假设死于第一关，零成本止损 |
| v1 首个外部试点 | 1 月 | 1 个 ICP 团队连续 7 天有上传，且 ≥3 次主动打开失败分诊页 | 持续上传但 14 天无人查看 → "解读有价值"被证伪 |
| v2 行为证据 | 3 月 | ≥1 团队基于榜单修复/隔离 ≥5 个用例；守门人自报"看红灯时间下降" | 看了但行为不变 → A5 失败，产品只是又一个仪表盘 |

### 总证伪声明

若 3 个月内找不到 1 个满足 ICP 的团队愿意加那 5 行 CI 配置——说明痛感判断错误，**问题不值得解，停止项目**。这一条写进 PRD 是为了让"停止"成为预先定义的合法结局，而不是失败。

## 9. 路线图

**v0（1 周）**：上传 API + TestCase 身份解析 + run 间 diff + 单页 Web（run 列表 + 失败分诊）。立即 dogfooding。
**v1（1 月）**：flaky 检测（同 SHA 翻转 + 跨 run 统计）、release verdict、钉钉/企微/飞书/Webhook 通知、PR comment、只读分享。
**v2（3 月，按 gate 证据排序）**：损失排序的资产健康榜、quarantine 工作流（显式开启）、MCP server、慢测试趋势、多仓聚合。
**远期（仅当出现付费级证据）**：执行选配（无 CI 团队的定时巡检）、merge 阻断模式、多租户 SaaS。

每一项 v2/远期功能启动前必须指出它对应的 gate 证据；没有证据，不动工。

## 10. 开放问题（诚实清单）

1. 用例改名导致履历断裂——自动探测（基于错误签名/文件路径相似度）值不值得做？v1 先给手动合并。
2. monorepo 多套件聚合的身份命名空间如何切——按上传 token、按目录、还是显式 suite_id？需要首个 monorepo 用户的真实结构再定。
3. flaky 判定算法的两条路线（同 SHA 翻转 = 高置信低召回；跨 run 统计 = 高召回需控误报）权重如何配——v1 用保守版（只报同 SHA 翻转 + 极高翻转率），宁可漏报不可误报（A4）。
4. 免费/收费切分（若走开源 + 商业版）：单机开源全功能、多租户/SSO/审计收费是国内可行模式（MeterSphere 路径），但需先过 v1 gate 再设计。

## 附录 A：竞品格局速览（2026-06 调研）

| 产品 | 形态 | 关键启示 |
|------|------|----------|
| Trunk Flaky Tests | CI 上传 + runtime quarantine（覆盖 exit code） | 信号要能改变下游行为（A5 的来源之一）；quarantine 是留存功能 |

| Currents | Playwright 垂直报告 + 编排 | 垂直框架打法可行，但天花板低 |

共同点：**没有一家要求用户迁移测试执行**。这是 A3 最强的外部佐证。

## 附录 B：与现有 qa_platform 的资产映射（唯一引用现状的一节）
