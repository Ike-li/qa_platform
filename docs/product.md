# QA 自动化执行平台 — 产品需求与试点边界

> §1–§8 描述产品目标与验收意图，§9 描述当前试点产品化边界（Beta / GA 准入）；当前 `main` 的实现状态以 [`feature-catalog.md`](feature-catalog.md) 和 [`TODO.md`](TODO.md) 为准。

## 1. 产品定位

一句话：**让测试执行变得可复现、可观测、可比较。**

QA 自动化执行平台是一个专注于"测试执行"环节的内部工具。它不写测试、不做构建、不做部署——它只做一件事：接收测试代码，在隔离环境中执行，产出结构化结果，并让对的人在对的时间看到对的信息。

### 1.1 核心价值主张

| 价值 | 说明 |
|------|------|
| 执行可复现 | 同样的输入永远产出同样的结果，不受环境漂移影响 |
| 结果可比较 | 当前主路径聚焦跨时间质量变化；跨环境、跨分支专属对比视图作为远期增强，不纳入当前验收 |
| 反馈可达 | 测试失败时，相关人员立即收到精准通知 |
| 过程可观测 | 执行全程实时可见，不是提交后干等 |

### 1.2 不做什么

- 不写测试（那是开发者的事）
- 不做代码构建（那是 CI 的事，平台假设代码已可执行）
- 不做部署（那是 CD 的事）
- 不做测试用例管理（那是 TestRail/Xray 的事，但可对接）

## 2. 用户画像

### 2.1 QA 工程师（主要用户）

**典型画像：** 负责 5-15 个项目的自动化测试维护，日均触发 20-50 次执行，每次查看结果花费 2-5 分钟。

**日常场景：** 管理多个项目的自动化测试，频繁触发执行、查看结果、分析失败原因。

**痛点：**
- 本地跑测试环境不一致，结果不可信
- CI 里的测试日志难以实时查看，只能等结束
- 失败用例的历史趋势无从追踪，不知道是新 bug 还是 flaky test

**期望：**
- 一键触发，实时看日志
- 失败时快速定位：是环境问题还是代码问题
- 看到某个用例最近 N 次的通过率趋势

### 2.2 开发者

**典型画像：** 每天提交 3-5 次代码，关注自己改动是否破坏测试，不愿花超过 1 分钟在测试平台上。

**日常场景：** 提交代码后想快速知道是否破坏了现有测试。

**痛点：**
- CI 反馈太慢，排队等很久
- 测试报告格式不统一，不同项目看不同地方

**期望：**
- 提交后自动触发，几分钟内出结果
- 统一的结果视图，不用学习不同工具

### 2.3 测试经理 / 研发经理

**典型画像：** 管理 3-5 个团队，每周查看质量报告 2-3 次，发布前集中关注。

**日常场景：** 需要了解整体质量状况，做发布决策。

**痛点：**
- 质量数据散落在各处，没有统一视图
- 无法快速回答"这个版本能不能发"

**期望：**
- 项目级质量仪表盘：通过率趋势、失败热点、覆盖率变化
- 项目级质量仪表盘；跨分支/跨环境专属对比视图为远期增强，当前不作为验收项

### 2.4 外部系统（CI/CD、通知平台）

**集成场景：** 通过 API 或 Webhook 与平台交互。

**期望：**
- 完整的 REST API，支持触发执行、查询结果
- Webhook 回调，执行完成后通知外部系统
- 标准化的结果格式，便于下游消费

## 3. 功能需求

### 3.1 项目管理

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-PM-01 | 创建项目 | 关联 Git 仓库，配置默认分支 | 支持 HTTPS/SSH 两种认证方式；创建后可立即触发执行 |
| F-PM-02 | 凭证管理 | 安全存储 Git Token/SSH Key | 凭证加密存储；仅项目成员可使用；支持轮换 |
| F-PM-03 | 项目归档 | 停用项目但保留历史数据 | 归档后不可触发新执行；历史数据仍可查询 |

### 3.2 执行管道（Pipeline）

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-PL-01 | 定义管道 | 配置测试运行器、结果收集器、超时、重试策略 | 每个项目可定义多条管道（如 unit/integration/e2e） |
| F-PL-02 | 环境配置 | 指定 Docker 镜像、环境变量、资源限制 | 环境变量加密存储；支持按环境隔离（dev/staging/prod） |
| F-PL-03 | 资源限制 | 限制单次执行的 CPU/内存/产物大小 | 内存超限时发送 SIGTERM，等待 30s 后 SIGKILL；状态标记为 timeout；日志记录终止原因和资源用量 |

### 3.3 测试执行

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-EX-01 | 手动触发 | 通过 Web UI 或 API 触发执行 | 可指定分支/commit/管道/环境；触发后 < 5s 进入队列 |
| F-EX-02 | 定时触发 | Cron 表达式定时执行 | 支持时区；支持静默窗口（如发布冻结期不触发） |
| F-EX-03 | Webhook 触发 | Git push/PR 事件自动触发 | 支持分支过滤；支持去重（同 commit 不重复触发） |
| F-EX-04 | 执行隔离 | 每次执行在独立容器中运行 | 默认网络策略为 `deny`，容器不可访问宿主网络；如测试安装依赖需联网，必须由环境显式设置 `allow` 或 `restricted`；执行结束后容器销毁 |
| F-EX-05 | 实时日志 | 执行过程中实时推送日志 | 延迟 < 2s；支持断线重连；日志持久化可回看 |
| F-EX-06 | 取消执行 | 支持取消正在运行的执行 | 取消后 < 10s 容器终止；状态标记为 cancelled |
| F-EX-07 | 自动重试 | 基础设施失败（超时、OOM、容器异常）后按策略自动重试；测试断言失败不重试 | 可配置最大重试次数（1-5）；重试间共享 retry_group 便于关联；重试间隔可配置（默认 30s） |
| F-EX-08 | 优先级队列 | 支持执行优先级 | 高优先级任务插队；同优先级 FIFO |

### 3.4 结果与报告

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-RE-01 | 结构化结果 | 解析测试结果为统一格式 | 支持 JUnit XML；可扩展其他格式 |
| F-RE-02 | 执行摘要 | 展示通过/失败/跳过/错误数量和通过率 | 执行结束后 < 3s 生成摘要 |
| F-RE-03 | 失败详情 | 展示错误信息和堆栈 | 支持点击跳转到具体用例 |
| F-RE-04 | 产物管理 | 存储报告、截图、视频、覆盖率等产物 | 支持通过预签名 URL 下载（有效期 1 小时）；支持在线预览（HTML 报告） |
| F-RE-05 | 历史趋势 | 展示用例/项目级别的通过率趋势 | 支持按时间范围筛选；可识别 flaky test |

### 3.5 通知

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-NT-01 | 条件通知 | 按规则触发通知（如：失败时通知、通过率下降时通知） | 支持多条件 AND 与 OR 条件组；条件类型包括：状态变更、通过率阈值、失败用例数、连续失败次数 |
| F-NT-02 | 多渠道 | 支持邮件、钉钉、企业微信、Webhook；单条规则中每种一等渠道配置一次，邮件渠道用收件人列表覆盖多人通知；Slack 通过通用 Webhook 覆盖，不做一等渠道 | 每个渠道可独立配置模板 |
| F-NT-03 | 通知模板 | 自定义通知内容模板 | 支持变量替换（项目名、通过率、失败用例等） |

### 3.6 权限与多租户

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-AU-01 | 用户认证 | 用户名注册/登录，注册时收集 email | JWT Token；支持 Token 刷新 |
| F-AU-02 | API Token | 支持生成长期 API Token | 可配置 scope 和过期时间；支持吊销 |
| F-AU-03 | 角色权限 | 双层角色模型：租户级（Owner/Admin/Member/Viewer）+ 项目级（Admin/Developer/Viewer） | 租户 Viewer 全局只读；项目级角色控制具体项目内的操作权限；项目 Developer 可触发执行；项目 Admin 可管理项目配置 |
| F-AU-04 | 租户隔离 | 数据按租户隔离 | Project / Run 等聚合根按 tenant 过滤，子资源通过聚合根间接隔离；跨租户 ID 访问返回 404（非 403）；集成测试验证跨租户不可访问 |

### 3.7 列表与搜索

| ID | 功能 | 描述 | 验收标准 |
|----|------|------|----------|
| F-LS-01 | 执行列表过滤 | 按状态/管道/分支/时间范围过滤 Run 列表 | 支持多状态组合过滤；支持时间范围（start/end）；默认按创建时间倒序 |
| F-LS-02 | 分页 | 所有列表接口支持分页 | 返回 page/per_page/total；默认 per_page=20，最大 100 |
| F-LS-03 | 项目搜索 | 按名称模糊搜索项目 | 支持子串匹配（LIKE '%keyword%'）；结果按名称字母序排序 |
| F-LS-04 | 测试结果过滤 | 按状态/suite/关键字过滤测试结果 | 至少支持按 passed/failed/error/skipped 过滤；后端可透传 xfail 等扩展状态；支持 suite 名称过滤 |

## 4. 非功能需求

| 维度 | 指标 | 目标值 |
|------|------|--------|
| 响应时间 | 读 API p99 延迟 | < 100ms |
| 响应时间 | 写 API p99 延迟 | < 300ms |
| 吞吐量 | 并发执行数 | 单 Worker 节点 ≥ 10 并发容器 |
| 可用性 | 服务可用率 | ≥ 99.5%（月度） |
| 日志延迟 | 实时日志推送延迟 | < 2s |
| 数据保留 | 执行记录保留时间 | 默认 90 天，可配置 |
| 容量 | 单次执行最大日志量 | 约 40MB 日志 payload（Redis Stream 近似 MAXLEN 10000 条 + 单条 4KB 上限；非精确硬上限） |
| 容量 | 单次执行最大产物总大小 | 500MB |
| 容量 | Redis Stream 单 Run 日志缓冲 | 最近约 10000 条（MAXLEN auto-trim） |
| 安全 | 凭证存储 | AES-256-GCM 加密；内存中不留明文 |
| 安全 | 执行隔离 | 容器级隔离；默认网络策略不可访问宿主网络，联网需环境显式放开 |
| 安全 | API 防护 | 认证高风险端点 rate limit：5 次/分钟/限流桶；通用 API：100 次/分钟/限流桶；Bearer 请求按 token hash，其他请求按可信代理解析后的 IP |
| 可扩展 | Worker 水平扩展 | 加节点即加容量，无需停机 |

## 5. 用户旅程

### 5.1 QA 工程师：首次接入项目

```
创建项目 → 配置 Git 凭证 → 定义管道（选择运行器+收集器）
→ 配置环境（镜像+变量） → 手动触发首次执行 → 查看结果确认接入成功
→ 配置定时触发 → 配置失败通知
```

### 5.2 开发者：提交后查看结果

```
Git push → Webhook 自动触发执行 → 收到通知（或主动查看）
→ 查看执行摘要 → 如有失败，查看详情和堆栈 → 修复后重新提交
```

### 5.3 测试经理：发布前质量评估

```
打开项目仪表盘 → 查看最近 7 天通过率趋势 → 基于已有 branch 执行记录轻量对比 release / main（专属对比视图仍是远期增强）
→ 查看失败热点（哪些用例最常失败） → 判断是否可以发布
```

### 5.4 异常路径：执行超时

```
触发执行 → 等待中发现执行时间异常长 → 查看实时日志定位卡住位置
→ 手动取消执行 → 调整超时配置或修复测试代码 → 重新触发
```

### 5.5 异常路径：凭证过期

```
定时执行失败 → 收到通知"Git clone 失败：认证失败"
→ 进入项目设置 → 更新 Git 凭证 → 手动触发验证 → 恢复正常
```

### 5.6 异常路径：Worker 故障

```
执行中 Worker 进程崩溃 → 心跳超时（90s 无更新）
→ 平台自动标记 Run 为 failed（原因：worker_lost）
→ 目标体验：如配置了自动重试，自动创建新 Run attempt
→ 用户看到失败记录，可查看"worker 丢失"原因
```

当前 `main` 对 worker_lost 会标记 failed、清理 orphan container；如该 Run 的 retry policy 命中基础设施失败重试条件，worker reclaim callback 会创建新的 retry Run。nightly/manual external-stack 已覆盖 worker_lost 黑盒重试并验证 retry Run 的 artifact 与归档日志。

## 6. 路线图

以下是产品目标分期，不代表当前 `main` 已全部完成；当前完成度见 `feature-catalog.md` 与 `TODO.md` 的状态表。

### Phase 1: MVP（核心执行循环）

- 项目/管道/环境 CRUD（F-PM-01~03, F-PL-01~03）
- 手动触发执行（F-EX-01）
- Docker 容器隔离执行（F-EX-04）
- JUnit XML 结果收集（F-RE-01, F-RE-02, F-RE-03）
- 实时日志流（F-EX-05）
- 执行取消（F-EX-06）
- 用户认证和角色权限（F-AU-01, F-AU-03）
- 产物存储和下载（F-RE-04）
- 列表/分页/过滤（F-LS-01~04）

Phase 1 范围说明：
- F-AU-03 角色权限：Phase 1 实现租户级四角色（Owner/Admin/Member/Viewer）+ 项目成员关联 + 基础项目级权限（Admin 管理配置、Developer 触发执行、Viewer 只读）；双层权限交集解析在 Phase 1 实现
- F-RE-04 产物管理：Phase 1 实现预签名 URL 下载；HTML 报告在线预览延至 Phase 3
- 前端：Phase 1 仅交付 API + OpenAPI 文档 + 基础 React 19 管理界面（项目列表、执行触发、结果查看）
- 注册流程：Phase 1 注册即可用，无邮箱验证（Phase 2 补充）

### Phase 2: 自动化与通知

- Cron 定时触发（F-EX-02）
- Webhook 触发 + Webhook 配置管理（F-EX-03）
- 多渠道通知（F-NT-01~03）
- 自动重试（F-EX-07）
- 优先级队列（F-EX-08）
- API Token（F-AU-02）
- 租户隔离（F-AU-04）
- 批量操作（批量取消、批量重新触发）

### Phase 3: 洞察与报告

- 项目质量仪表盘
- 用例级历史趋势（F-RE-05）
- Flaky test 检测
- Allure 报告集成
- 系统状态页（Worker 数量、队列深度、成功率）

Phase 3 当前不纳入验收：
- 跨分支/跨环境专属对比视图
- 历史日志全文搜索
- 数据导出 CSV（测试结果、执行历史）

### Phase 4: 规模化

Phase 4 是远期方向，不纳入当前阶段验收：

- Kubernetes Job 执行后端
- 多 Worker 节点管理
- 历史数据归档与分区
- 更多第三方 Runner / Collector 扩展
- 开放插件市场

## 7. 成功指标

| 指标 | 基线 | 目标（上线 3 个月） | 推导依据 |
|------|------|---------------------|----------|
| 日均执行次数 | 0 | ≥ 100 | 假设 30 活跃用户 × 3-4 次/人/天 |
| 平均执行等待时间（排队到开始） | - | < 30s | 10 并发容器，峰值队列深度 < 5 |
| 测试结果查看率 | - | ≥ 80% | 执行完成后 24h 内有用户访问结果页 |
| 通知触达率 | - | ≥ 95% | 通知发送成功 / 通知触发总数 |
| 用户满意度（NPS） | - | ≥ 40 | 季度匿名问卷 |

## 8. 约束与假设

### 约束

- 团队规模小（< 5 人），不支撑微服务运维复杂度
- 初期部署在单机或小集群，需要渐进式扩展路径
- 需要支持中国大陆网络环境（钉钉/企业微信集成）

### 假设

- 用户的测试代码已经可以在容器中运行（平台不负责构建）
- Git 仓库可通过 HTTPS 或 SSH 访问
- 用户愿意提供 Docker 镜像或使用平台默认镜像
- 初期用户量 < 50 人，日执行量 < 500 次

## 9. 试点产品化边界（Beta / GA 准入）

> 更新于 2026-06-04。本节是当前产品化试点边界；§1–§8 为目标态，功能细账见 [`feature-catalog.md`](feature-catalog.md)。

### 目标用户

首批目标用户是 QA 工程师：已有一个自动化测试项目，需要把仓库、凭证、Pipeline、环境和 JUnit/Allure 结果接入平台，并稳定查看每日执行结果。

次级用户是 QA Lead / 测试经理：需要用轻量趋势、失败新增/恢复和 flaky 排除后的通过率判断一个 git ref 是否可进入下一步发布判断。

### 当前可承诺能力

- 项目接入：项目详情页提供接入状态面板，按 Git 配置、凭证状态、Pipeline、Environment、首次 Run 和通知可选项推导完成度；入口均复用现有配置页或触发弹窗。
- 首次试跑：用户可在项目详情页直接触发 Run，并在最近运行列表看到最新执行结果。
- 每日结果查看：项目详情页展示最近 Run；Run 详情页展示状态、失败摘要、测试结果、日志、报告/产物和重新触发入口。
- 失败排障：失败 Run 会突出失败摘要、失败/错误用例数、日志入口、报告/产物入口与 Re-run；失败用例展开后可跳到项目 Analytics 的单用例历史。
- Release 判断：Analytics 支持按 `git_ref` 过滤趋势和 flaky，提供 `release-summary` 摘要，包括 raw pass rate、flaky-adjusted pass rate、新增失败和恢复用例。
- 指标口径：试点指标先用现有数据计算，不新增埋点。

### 当前不承诺能力

- 完整跨分支 / 跨环境 diff 产品视图。
- GitLab / Gitee provider 的完整 webhook 事件矩阵。
- 多资源报告的统一报告中心体验。
- 长稳压测、完整容量墙和大规模队列公平性证据。
- 插件市场、Kubernetes Job 后端、多 Worker 节点管理等 Phase 4 能力。

### Beta 准入

Beta 可以接受以下限制：

- Webhook provider 以 GitHub push 主路径为主。
- 多资源报告体验仍偏弱，只要求 Run 详情页能进入报告和产物。
- 长稳压测尚未完成，但基础性能 smoke 和核心读写门禁要通过。
- 指标先采用可计算口径，不新增产品事件埋点。

Beta 必须满足：

- 一个 QA 工程师能从已有自动化项目完成接入、首次试跑并看到结果。
- 接入状态面板能明确显示 Git、凭证、Pipeline、Environment、首次 Run 的状态。
- 失败 Run 能从摘要进入日志、报告/产物、失败用例和重新触发。
- Analytics 能按目标 git ref 看趋势、flaky 和 release summary。

### GA 准入

GA 不能接受以下缺口：

- 首次接入没有明确引导。
- 核心 SLO 没有真实环境证据。
- Release 判断基础视图不可用。
- Run 详情页不能支撑失败定位的主流程。

GA 前需要补齐：

- 真实试点环境的 time-to-first-green-run、7 日内二次触发率、失败 Run 日志/产物查看率证据。
- 更清晰的接入验证动作证据，包括连接验证、JUnit 路径验证和试跑结果。
- 对多资源报告体验和长期稳定性压测给出明确达标或豁免结论。

### 试点准入条件

- 试点项目已有可运行的自动化测试和 JUnit XML 输出。
- 仓库访问方式明确：公开仓库、token 或 SSH key。
- 有一个可接受的基础镜像和运行资源上限。
- 试点团队愿意连续 7 天查看平台结果，并反馈接入、排障和 release 判断过程中的阻塞点。

### 成功指标（试点运营口径）

- `time-to-first-green-run`：从项目创建到首次无失败 Run 的时间。
- `7 日内二次触发率`：首次 Run 后 7 天内再次触发 Run 的项目占比。
- `失败 Run 的日志/产物查看率`：失败 Run 中至少查看日志或产物入口的占比。

辅助观察：

- 首次接入卡在哪个 checklist 项。
- 失败 Run 中是否进入单用例历史。
- Release 判断中目标 `git_ref` 与 baseline 对比是否足够回答“能不能继续发”。

### 下个里程碑

1. 收集 1-2 个真实 QA 项目的接入证据。
2. 把连接验证、JUnit 路径验证和试跑状态从“配置入口”升级为更明确的验证动作。
3. 补一轮真实环境的 Beta evidence：接入时长、首次 green、二次触发、失败排障路径。
4. 根据试点反馈决定是否投入完整跨分支 diff、多资源报告中心和更重的压测。
